Vision AI — Image Object Location Chatbot

Technical Documentation & Project Journey  |  Phase 1 Demonstration  |  Sep 2026

1. Project Overview

The goal of Phase 1 is to build an AI-powered chatbot that accepts a room image and a natural-language question — such as "Where is the key?" — and accurately identifies and locates the queried object inside the image, even when the object is tiny (a few dozen pixels in a 1280×960 photo).

Phase 1 Target
Given any room image + a user's free-text question, detect the object and respond with its exact location in the scene. No pre-defined object classes. No bounding-box requirements from the user side.
Phases at a Glance
Phase 1 (current) — Single image + chatbot query → locate item
Phase 2 — Video input → temporal tracking ("key picked up at 11:03")
Phase 3 — Live camera → threat detection (unattended suitcase alert)
Hardware Environment
MacBook Pro — Apple Silicon (ARM64)
Device: MPS (Metal Performance Shaders)
Python 3.9.6 · torch 2.8.0 · transformers 4.57.6
No external GPU server

2. The Test Image & The Challenge

The primary test image (images/img01.jpg, 1280×960 px) shows a room with a person standing behind a brown leather sofa. A Dell laptop is open on the sofa. Two keys are hidden in the scene:

🔑 Key 1 — Sofa Armrest
A small silver house key lying flat on the right armrest of the brown leather sofa.

Size: ~70 × 30 px in a 1280×960 image
Occupies: 0.17% of total image area
Classification: TINY object
🔑 Key 2 — Door Lock
A key inserted into the lock cylinder of the wooden door, right side of the room.

Size: ~15 × 35 px in a 1280×960 image
Occupies: 0.04% of total image area
Classification: TINY object
Core Technical Challenge
Both keys are extremely small relative to the full image. Any model that internally downscales the image (e.g. to 336×336 or 448×448) will reduce a 70px key to ~18px — making it effectively invisible to standard Vision Language Models.

3. The Journey — Models Tried & Why They Failed

Attempt 1 — YOLO (You Only Look Once)
Why tried: Industry-standard real-time object detector, fast, widely deployed.
Problem: YOLO is trained on a fixed set of 80 COCO classes (person, car, chair…). "Key" is not a reliable class. Cannot detect arbitrary objects by text query — no open-vocabulary support.
✗ Failed: Could not detect keys. Too few object classes for real-world room queries.
Attempt 2 — Grounding DINO
Why tried: Open-vocabulary detector — accepts free-text queries. Strong academic benchmark results.
Problem: Tiny object detection weakness. Grounding DINO uses a feature pyramid but still struggled with objects occupying less than 0.2% of the image area. The key at ~70px was consistently missed or produced very low-confidence detections below any usable threshold.
✗ Failed: Did not detect the armrest key reliably.
Attempt 3 — Qwen2.5-VL-7B (Vision Language Model)
Why tried: Large VLM with strong scene understanding. Can answer natural-language questions about images.
Problem 1 — Resolution loss: Qwen internally processes images at 448×448 or tiled crops. A 70px key becomes ~18px — invisible.
Problem 2 — Coordinate hallucination: Outputs bounding boxes as text tokens (<box>371,524,612,748</box>). Token generation is stochastic — the same query produces different coordinates each run. Boxes drift by 50–200px.
Problem 3 — Ambiguity: The model uses normalized 0–1000 coordinates internally but sometimes outputs raw pixels — no consistent interpretation possible.
✗ Failed: Never found either key. Coordinates unreliable even when it "described" the correct location.
Attempt 4 — SAM (Segment Anything) + VLM Two-Stage Pipeline
Why tried: SAM generates pixel-perfect masks for every region; a VLM then classifies each region.
Problem 1 — Scale: SAM generates 100–300 mask proposals per image. Running a VLM on each is extremely slow (~15–30 minutes per query on MPS).
Problem 2 — Word boundary collision: When classifying "key", the VLM matched the word "key" inside "keyboard" — constant false positives from the laptop keyboard region.
Problem 3 — Door key missed: The door lock key region was too small for SAM to isolate as a clean mask.
✗ Abandoned: Too slow and too many false positives for Phase 1 interactive use.
Attempt 5 — Florence-2-large (Microsoft)
Why tried: Microsoft's vision foundation model — DaViT encoder trained on 5.4B image-text triples. Supports <OPEN_VOCABULARY_DETECTION> and <CAPTION_TO_PHRASE_GROUNDING> task tokens.
MPS fixes required: attn_implementation="eager" (avoids SDPA crash), use_cache=False (past_key_values returns None on MPS), dtype= not torch_dtype=.
Success: "door key" → ✓ perfect detection. "sofa" → ✓ perfect.
Remaining problem: Query "key" → detected the necklace pendant on the person instead of the armrest key. The pendant visually resembles a key at feature-map resolution.
⚠ Partial: Good for scene understanding; inconsistent for generic single-word tiny-object queries.
Final Solution — OWLv2-large (Google)
Why tried: Purpose-built open-vocabulary object detector. Processes image as a full-resolution patch grid. No language generation — direct box regression from visual-text similarity.
Result: Found both keys correctly with clear confidence score separation.
✓ Key 1 (armrest): score 0.347 · box [886, 718, 938, 737]
✓ Key 2 (door lock): score 0.261 · box [975, 455, 983, 483]
✗ False positives: score ≤ 0.170 — cleanly separable with threshold 0.20
✓ Selected as the production model for Phase 1.

Key Technical Decisions

DecisionChoiceReason
Model variantowlv2-large-patch14-ensembleLarge > Base — higher confidence gap, better tiny-object separation
Threshold0.20Empirically determined — separates true keys (≥0.261) from all false positives (≤0.170)
NMS strategyIoU + containment checkOWLv2 fires sub-region duplicates on tiny objects — standard IoU misses them; containment check catches them
DeviceMPS (Apple Silicon)float32 — float16 causes NaN on some Mac configs
Prompt format"a photo of a {item}"OWLv2 was trained on this CLIP-style format — produces higher scores than bare words
