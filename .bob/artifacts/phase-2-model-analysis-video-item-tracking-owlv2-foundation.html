Phase 2: Video Item Tracking — Model Analysis

Revised analysis grounded in the confirmed Phase 1 final stack: OWLv2-large-patch14-ensemble (not Qwen). Qwen was ruled out due to hallucination and tiny-object detection failures.

1. Why OWLv2 is the Phase 1 Winner

OWLv2-large-patch14-ensemble (google/owlv2-large-patch14-ensemble) won Phase 1 for three architectural reasons:
  • No language generation — produces boxes directly via patch-similarity scoring, not token prediction. This eliminates the coordinate hallucination that plagued Qwen2.5-VL.
  • Full-resolution patch grid — the image is divided into fine-grained patches, each compared against the text embedding. Small objects (key on armrest) are caught because no spatial downsampling occurs before matching.
  • Detection-trained, not instruction-tuned — OWLv2 was trained exclusively on detection tasks (OWL-ViT v2 distillation on COCO, Objects365, OpenImages). It has no "conversation" mode to drift into.

This matters for Phase 2 because the same properties — no hallucination, patch-level precision, deterministic box output — are exactly what a reliable per-frame object tracker needs as its detection backbone.

2. What Phase 2 Must Do

Input: Video file + natural language query (e.g. "where is the key?")
Required output: "At 11:03 min, the person picked up the key and placed it in their pocket."

Core capabilities needed:
  • Detect a specific item reliably in each video frame — especially tiny objects
  • Track that item across frames (handle occlusion, fast motion)
  • Detect when an action happens: someone picks up / moves / places the item
  • Produce a timestamp-anchored natural language answer
  • Handle videos of several minutes length

This splits into two clearly separable sub-problems: (A) frame-level detection + tracking and (B) temporal reasoning + narrative generation. OWLv2 solves A; a different model is needed for B.

4. Stage 2 — Tracker Model Candidates

ByteTrack
ByteDance Research · 2022 · pip: supervision / lap
No weights — algorithm only (Hungarian + Kalman)
★ Recommended Tracker

ByteTrack is a detection-agnostic tracker: it takes any bounding box list per frame and uses Kalman filtering + Hungarian matching to assign persistent IDs. It uses both high-score and low-score detections to handle occlusion — exactly what OWLv2's variable-confidence output needs.

✔ Strengths

  • Works directly with OWLv2's box output (no model change)
  • Handles occlusion by using low-confidence detections in a second pass
  • Very lightweight — pure NumPy/SciPy, runs on CPU instantly
  • Available in supervision library (Roboflow): one-line install
  • Tracks multiple objects simultaneously (key + person)
  • State-of-the-art on MOT17/MOT20 benchmarks

✗ Limitations

  • ID switches on very long occlusions (object fully hidden >5s)
  • Requires consistent detection rate (≥1 fps for stable tracks)
SAM 2 (Segment Anything Model 2)
Meta AI · 2024 · pip: sam2
~80M (SAM2-hiera-small) to 224M (SAM2-hiera-large)
Strong — Pixel Precise

SAM 2 extends segment-anything to video. Given a bounding box (from OWLv2) on frame 0, SAM 2 propagates a pixel-precise mask of the object across all subsequent frames — including through occlusion and scale changes. Best choice when you need to show exactly where the object is in each frame, not just a bounding box.

✔ Strengths

  • Pixel-level tracking — produces full segmentation mask per frame
  • Can be initialised with OWLv2's bounding box directly
  • Handles scale change, rotation, partial occlusion
  • Produces annotated video output (key highlighted in every frame)
  • Runs on MPS (Apple Silicon) with float32

✗ Limitations

  • Heavier than ByteTrack — ~2–4 GB VRAM for large model
  • New dependency (sam2 package from Meta)
  • Best used for the output annotation layer, not the core event detector
  • Loses track if object fully disappears (expected — in a pocket)
DeepSORT
Wojke et al. · 2017
Older — Skip

DeepSORT requires a dedicated Re-ID feature extractor trained on person datasets. The Re-ID model adds complexity and doesn't improve over ByteTrack for object tracking (only helps for person re-identification). ByteTrack supersedes it.

5. Stage 4 — Narrative / Reasoning Model Candidates

Once the tracker produces an event list (e.g., key disappeared at frame 662, person was 40px away at frame 660), a model needs to reason about it and produce the human-readable answer. Two viable paths:

Path A — Structured Event → LLM (No Vision)

The tracker outputs a structured event log. A text-only LLM (or even a rule-based formatter) reads the log and produces the narrative. No video vision needed at this stage.

Example input to LLM:
"key detected at [823,610] frames 0–661. Disappeared at frame 662. Person bbox [780,580] at frame 660. Video fps=1. Frame 662 = 11:02 min."

Example LLM output:
"At 11:02 min, the key disappeared from the armrest. A person was within close proximity at that moment, suggesting they picked it up."
Qwen2.5-7B-Instruct (Text Only)
Alibaba · Already available as transformers model
7B — text-only (no vision), very fast on MPS
★ Best for Path A

The text-only Qwen2.5 Instruct model is an excellent narrator — it takes structured tracker output and produces natural, fluent descriptions. Critically, it does not look at images, so Qwen's vision hallucination problem is completely irrelevant here. It only needs to reason about numbers and produce text.

✔ Strengths

  • Qwen family — already familiar, same tokeniser ecosystem
  • Text-only: no hallucination risk on visual data
  • Very fast on MPS/CPU — tracker events are short text
  • Excellent at temporal reasoning ("before", "after", "at time T")
  • Can be replaced with any local Ollama model (llama3, mistral)

✗ Limitations

  • Cannot describe what the scene looks like — only what the tracker reports
  • If tracker is wrong, narrator will be wrong (garbage-in-garbage-out)

Path B — Frame Snapshot + VLM (Vision Confirmation)

At the detected event timestamp, extract a small clip (±5 seconds). Feed that clip's key frames + the tracker's event data to a Video LMM to produce a richer, visually-grounded answer.
InternVL2.5-8B (Short Clip Mode)
Shanghai AI Lab · 2024
8B — open source, runs on MPS
Best for Path B

InternVL2.5-8B processes up to ~16 frames at high resolution. Used on a 10-second event clip (extracted by the tracker), it can confirm "yes, the person is holding the key" and produce a visually-grounded sentence. Critically, it's only asked about a short clip — not a 30-minute video — so hallucination risk is low.

✔ Strengths

  • State-of-the-art on short-video VQA (Video-MME benchmark)
  • 8B fits on MPS with float16
  • Excellent at describing human-object interactions
  • HuggingFace native — same AutoModel pattern
  • Open source, no API cost

✗ Limitations

  • New dependency — different model family from Phase 1
  • Adds ~8 GB model weight download
  • Still can hallucinate on ambiguous frames
Qwen2.5-VL-7B (Video Mode)
Alibaba · Phase 1 tested
✗ Ruled Out — Same Problems
Qwen2.5-VL hallucinated on object detection and failed tiny-object detection in Phase 1. These are architectural limitations of its vision encoder and language generation approach — they would surface identically in a video context. Running it over video frames would produce the same hallucinated coordinates and missed small objects at scale. Not recommended.
Video-LLaVA (2023)
PKU-YuanGroup
Too Limited

8 frames maximum, no timestamps, weaker than InternVL2.5. Not worth integrating.

7. Final Recommendation

★ Primary Stack: OWLv2 (detect) + ByteTrack (track) + Qwen2.5-7B text (narrate)

Why this combination wins

  • OWLv2 is already the proven detector — reuse the exact same model, weights, threshold logic, NMS, and query expansion from Phase 1 on each video frame. Zero new detection risk.
  • ByteTrack is detection-agnostic — it only needs a list of [x1,y1,x2,y2, score] per frame, which is exactly what OWLv2 already returns. One pip install supervision or a 200-line pure-Python implementation.
  • Qwen2.5-7B text-only narrates events, not pixels — it never looks at an image, so the vision hallucination problem is completely bypassed. It only reads structured text like "key disappeared at 11:02, person 38px away" and produces natural language.

How the answer "At 11:03 min, the person put the key in their pocket" is produced

  1. OWLv2 detects "key" and "person" in every sampled frame (1 fps).
  2. ByteTrack assigns persistent IDs — key gets Track ID 3, person gets Track ID 1.
  3. Disappearance detector: Track ID 3 (key) last seen at frame 662 (= 11:02). Person Track ID 1 was 38px from the key at frame 661.
  4. Event log: {frame: 662, event: "key_disappeared", person_proximity: "close", timestamp: "11:02"}
  5. Qwen2.5-7B text reads: "Key was last seen at 11:02. A person was close to it at that moment. What happened?" → "At 11:03, the key was picked up by the person standing nearby."
Optional Layer: SAM 2 to produce an annotated output video clip showing the key's tracked path
